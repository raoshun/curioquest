# 13. 音声キャッシュによるレスポンス性改善（検討）

定型文を組み合わせて会話する場面では、合成音の再生成を打ち切ってキャッシュを
返せる。本ドキュメントは現行の会話フローの整理と、音声合成キャッシュの設計方針
を記載する。実装はしていない(検討フェーズ)。

関連: 02-features.md 4-1(対話フロー)、03-architecture.md 10/12、
05-safety-quality.md(音声データの保存方針)

## 13-1. 現行フローとレイテンシの内訳

`POST /api/sessions/{id}/voice` は 1 リクエストで次を行う(03-architecture 12)。

```text
音声アップロード
  → STT(faster-whisper)
  → 対話エンジン
      ├─ 固定応答ターン: LLM 呼び出し 0 回
      └─ 通常/ヒントターン: LLM 1〜2 回(応答生成 + 思考評価)
  → TTS(VOICEVOX /audio_query + /synthesis の 2 HTTP コール)
  → テキスト + WAV を返却
```

決定的なポイント:

- **通常ターン**は LLM が支配的で、TTS を削っても体感は大きくは良くならない。
- **固定応答ターン**(下表)は LLM を呼ばないため、ローカル環境のみでも
  **TTS が応答時間の大半**を占める(ローカル VOICEVOX でも 2 コールで数百 ms 程度、
  初回・長い文はさらに増える)。実測は 13-6 の計測項目に従う。
- TTS は同じテキスト・同じ声でも毎回再生成している。キャッシュは無い。

エンジンが返す固定応答(`engine.py` の定数)は現状 5 種で、すべて定型文である:

| 定数 | 場面 |
|---|---|
| `_REPEAT_REQUEST` | 認識空(無発話)の聞き直し |
| `SAFETY_REPLY` | 危険話題(7-1) |
| `_FAREWELL_REPLY` | こどもの終了 |
| `_TIME_UP_REPLY` | 利用時間到達 |
| `_IDLE_REPLY` | 無操作タイムアウト |

`_REVIEW_LEAD` / `_NO_SUMMARY_REVIEW` など振り返り文も固定部分を持つ。

## 13-2. 定型文対話モードの位置づけ

「定型文を組み合わせて話せる」構成とは、こどもの入力を既知の候補集合
(選択肢ボタン + その通りに読む音声入力)に限定するモードである。この場合:

1. **入力が閉集合になる** → 発話候補が列挙でき、STT 依存時は候補 ID 直接判定で
   現行のキーワード照合(`rules.detect_intent`)より誤検出が減る
   (05-safety-quality「音声認識の誤りを意図として扱わない」に親和)。
2. **応答が準閉集合になる** → 各候補 × 各状態でのエンジン応答は
   「固定応答」または「LLM 生成 + 固定フレーミング」。うち固定応答分(13-1 の表)は
   完全に予測可能で、事前が成立する。
3. レイテンシのボトルネックが LLM から音声出力へ移るため、**TTS キャッシュの
   効果が最も出る**のはこのモードである。

## 13-3. キャッシュ設計方針

### レイヤー

合成器の**アダプタ層にデコレータとして追加**する(`CachingTts(TextToSpeech)` のような
ラッパで `synthesize(text, voice)` を包む)。エンジン・API はキャッシュを知らない
ままでよく、`AudioError` の例外意味(テキスト第一優先のフォールバック)も不変。

###キー

`SHA-256(エンジン種別 + バージョンタグ + text + speaker_id + speed_scale + pitch_scale)`
をファイル名にする。

- 声の設定(話者・語速・音高)が変わればキーが変わるため、**能動的な無効化処理は
  不要**(古いエントリの残骸は 13-4 の容量管理で回収)。
- VOICEVOX Engine の更新で声質が変わる場合に備え、バージョンタグを含める
  (初期は設定値の手動管理でよい)。

### 保存

- メモリ LRU + ディスク(`data/tts_cache/` 配下の WAV。`db_path` と同じデータ領域)。
- ディスクヒット時は WAV を読み返すだけなので数 ms オーダー。
- キャッシュディレクトリは git 外(`.gitignore` 対象)とし、保護者画面から削除可能にする。
- **05-safety-quality の「音声を保存しない」はマイクロホン入力に関する制約**であり、
  合成出力のキャッシュは該当しない。ただし個人宅のディスクに子どもの音声に
  関わるファイルが残る以上、削除手段は用意する。

### 動作規則

1. ヒット(メモリ→ディスクの順)なら合成せず返す。
2. ミスなら合成し、成功時のみ書き込む。合成失敗時は従来通り `AudioError` を伝搬し、
   API 側のテキストのみフォールバック(`voice_available=false`)を維持する。
3. 同一キーの同時ミスはロックで 1 回の合成に寄せる(多重合成の防止)。
4. 事前ウォーム: 起動時(またはキャラクター追加時)にバックエンドタスクで
   13-1 の固定応答 × 設定済みキャラクター分を合成しておく。起動はブロックしない。
   定型文対話モードでは候補集合 × 状態の組み合わせも事前合成対象にできる。

## 13-4. 容量・削除

- 対象は定型文中心なので個数が小さい。固定応答 5 種 × キャラクター 3 体でも 20
  ファイルに収まり、事前合成を広げても 100 件オーダーである。
- 上限は合計バイト数(例 100MB)の LRU で回収。それ以上の細分化(世代管理・
  TTL)は初期は不要。

## 13-5. キャッシュしないもの(原則)

- **LLM 生成応答**: 同じ発言でも会話文脈で応答が変わるため、テキスト単位キャッシュは
  誤った文脈の再生リスクがある。将来 LLM 応答のプリフェッチ(応答生成と TTS の
  パイプライン化・先読み)は別テーマとして切り分け、ここでは行わない。
- **個人名補間入り定型文**「〇〇ちゃん」等で個人名が埋め込まれる文言は、現状の
  エンジン定数には存在しない。将来追加する場合は名前をキーに含めるか、
  補間部と固定部を分けて固定部だけキャッシュする。
- マイク入力音声: 現行方針どおり STT 後破棄(13-3 参照)。

## 13-6. 効果測定と実装順

先に計測し、後で実装する:

1. `/voice` の STT / エンジン / TTS 各区間の時間計測(ログにミリ秒単位の区分別記録を追加)。
2. 固定応答ターンが実利用に占める割合と、キャッシュ想定ヒット率の把握。

実装は小さく分ける:

| 段階 | 内容 |
|---|---|
| A | レイテンシ計測の追加 |
| B | `CachingTts` デコレータ(ミス時合成・メモリ + ディスク・キー設計) |
| C | 固定応答の起動時ウォームアップ |
| D | 定型文対話モード(入力の候補化)と候補 × 応答の事前合成 |

B だけで固定応答ターンの TTS 相当の応答時間がゼロに近づき、既存の
テキスト第一優先・エラーフォールバックの設計はそのまま保てる。

---

## 検討まとめ(会話フロー設計上の確認事項)

- 定型文モードは STT 誤作動耐性とレスポンス性の両面で現行設計と相性が良い。
  意図判定は候補 ID → 意図の対応表に置き換えられ、`rules.py` のキーワード照合は
  フォールバックに格下げできる。
- 固定応答はすでに「LLM を呼ばない閉集合」として設計されており、音声キャッシュの
  差し込み口としてアダプタ層が適切であることは現行構造が保証している。
- 最大の効果が得られるのは固定応答ターンであり、LLM ターンの体感改善はこの
  キャッシュでは期待しない(別アプローチ)。
