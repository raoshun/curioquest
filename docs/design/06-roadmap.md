# 16. 開発ロードマップ

段階的に開発することを推奨する。

| フェーズ | 内容 | 完了条件 | 進捗 |
|---|---|---|---|
| Phase 0 | 技術検証 | STT・LLM・TTSの連携 | 完了 |
| Phase 1 | 音声対話MVP | 子どもと自然な対話ができる | 完了 |
| Phase 2 | キャラクター・ミッション | 3種類の対話体験 | 完了 |
| Phase 3 | スタンプ・利用制限 | ゲーム進行が成立する | 完了 |
| Phase 4 | Memory・保護者画面 | 子ども別の継続体験 | 完了 |
| Phase 5 | 家庭内実運用 | 安定性・教育的品質の改善 | 未着手 |
| Phase 6 | 大人向け拡大 | 大人アカウント・年齢を参考にした対話・Python学習ミッションが使える | 未着手 |

## Phase 0：技術検証

最初に確認したいのは、以下の3点である。

- faster-whisperで子どもの発話を認識できるか
- LLMが短く自然な対話を継続できるか
- VOICEVOXで適切なテンポの音声を再生できるか

この3つを一連の音声対話として動かす。

## Phase 1：音声対話MVP

子どもアカウントを1つ作成し、ミッションを1つ実行できる状態にする。
最初はゲーム要素もキャラクター選択も不要である。
まず、子どもが実際に話したくなる対話を実現する。

## Phase 2：キャラクターとミッション

3種類のキャラクターを実装する。
同じ質問でもキャラクターによって思考の促し方が変わることを確認する。

## Phase 3：ゲーミフィケーション

スタンプと今日の冒険を追加する。
この段階で、利用時間制限と終了演出も実装する。

## Phase 4：長期記憶と保護者画面

子どもごとのMemoryを追加する。
過去の会話を踏まえたミッション生成と、今日の発見の表示を実装する。

## Phase 5：実運用

実際に家庭内で継続利用し、以下を改善する。

- 子どもが自発的に利用したくなるか
- AIの質問が難しすぎないか
- 音声認識の失敗が多くないか
- 対話が長引きすぎないか
- スタンプ獲得が適切か
- Memoryが正しく活用されているか

## Phase 6：大人向け拡大

対象を大人へ拡大し、登録情報とミッションの幅を増やす。

1. 大人アカウントの登録・切り替え（F01 3-1・3-2）。
2. 新規登録時の生年月日必須入力と、既存利用者への入力促し（F01 3-3）。
3. 年齢を会話レベルの参考材料として対話コンテキストへ注入（F02 4-4）。
4. スキル習得ミッションとして Python とそのライブラリ活用を追加（F04 6-5）。

完了条件：

- 大人ユーザーが登録し、大人向けの会話レベルで音声対話できる。
- 子どもと大人で会話の語彙・例え話を明確に切り替えられていることを確認できる。
- Python学習ミッションで、答えを直接教えずに対話を進められること。
- 登録時に生年月日を入力しないと新規登録できないこと（未来日付等はエラー）。

# 17. MVPの受け入れ基準

開発完了を判断するため、具体的な基準を定める。

| ID | 受け入れ条件 |
|---|---|
| AC-01 | 複数の子どもアカウントを登録・切り替えできる |
| AC-02 | 子どもごとに会話履歴が分離される |
| AC-03 | マイクから音声入力してAIと対話できる |
| AC-04 | AIの回答がVOICEVOXで再生される |
| AC-05 | 3種類のキャラクターを選択できる |
| AC-06 | 3種類のミッションを実行できる |
| AC-07 | 正解しなくてもミッションを完了できる |
| AC-08 | 思考過程に応じたスタンプを獲得できる |
| AC-09 | 利用時間の上限をバックエンドで制御できる |
| AC-10 | ミッション終了後に自然な終了演出がある |
| AC-11 | 保護者が利用状況を確認できる |
| AC-12 | 子ども単位でデータを削除できる |

MVPでは、特に AC-03、AC-04、AC-06、AC-07、AC-08 を重視する。
このアプリの価値は、音声で会話できること自体ではなく、会話によって思考を促すことにあるためである。

# 18. MVPの成功指標

一般的なアプリでは利用時間や継続率が重視されるが、このアプリでは少し違う評価軸を採用する。

| 指標 | 確認したいこと |
|---|---|
| 自発的な質問数 | 子ども自身が疑問を持つようになったか |
| 理由を説明した回数 | 考えを言語化できているか |
| 仮説を立てた回数 | 自分なりの答えを考えているか |
| 別の可能性を考えた回数 | 多角的な思考ができているか |
| ミッション完了率 | 難易度が適切か |
| 音声認識成功率 | UXに問題がないか |
| 保護者の評価 | 家庭内で有用だと感じられるか |

これらは成績として扱わず、対話設計の改善に利用する。
また、数値の増加だけで思考力が向上したと判断しないようにする。

# 19. 最終的な開発方針

本構想を実装するうえで、推奨する開発順序は次表のとおりである。

| 順位 | 開発対象 | 理由 |
|---|---|---|
| 1 | 音声対話エンジン | アプリの根幹 |
| 2 | 対話制御・思考促進ロジック | 教育的価値の根幹 |
| 3 | キャラクター | 子どもが親しみを持つため |
| 4 | ミッション | 毎日の利用目的を作る |
| 5 | スタンプ | 達成感を作る |
| 6 | 子ども別Memory | 継続利用の価値を高める |
| 7 | 保護者画面 | 家庭内での運用を支える |

特に、対話制御は独立したモジュールとして設計すること。
単にLLMのシステムプロンプトに教育方針を書くだけでは、モデルによって振る舞いが変わり、安定した教育体験を作れない。

LLMの能力を活用しつつ、対話の進行・報酬・利用制限はアプリケーション側で管理する構成が適切である。

最終的には、単なる音声チャットではなく、子どもの興味・思考・発見が蓄積されていく、家庭内のローカルAI知育プラットフォームを目指す。
