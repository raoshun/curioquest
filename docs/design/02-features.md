# サブシステム機能仕様（F01〜F07）

本アプリの中核は F02（音声対話）であり、対話制御エンジンが教育的価値を支える。
アプリ全体の方針・設計原則は [01-overview.md](01-overview.md) を参照のこと。

---

# 3. F01：ユーザー管理

## 3-1. アカウント構成

家庭単位で管理し、その下に複数の子どもアカウントと大人アカウントを設ける。
大人とは、保護者本人など子ども以外の利用者であり、自分自身の対話体験のためにアカウントを持つ。

```text
Family
 ├── Parent
 │    ├── Settings
 │    └── Dashboard
 │
 ├── Child A
 │    ├── Profile
 │    ├── Preferences
 │    ├── Progress
 │    └── Memory
 │
 ├── Child B
 │    ├── Profile
 │    ├── Preferences
 │    ├── Progress
 │    └── Memory
 │
 ├── Adult A
 │    ├── Profile
 │    ├── Preferences
 │    ├── Progress
 │    └── Memory
 │
 └── Child C
      └── ...
```

## 3-2. ユーザープロフィール（子ども・大人）

子ども・大人を問わず、すべてのユーザーが同じプロフィール構造を持つ。

管理項目：

| 項目 | 内容 |
|---|---|
| child_id | 一意の識別子（大人アカウントも含む共通識別子） |
| user_type | 利用者種別（child / adult） |
| nickname | 呼び名 |
| birthday | 生年月日（登録時に必須入力） |
| favorite_topics | 興味のあるテーマ |
| favorite_character | お気に入りのキャラクター |
| difficulty_profile | 領域別の難易度 |
| daily_limit | 1日の利用上限（大人アカウントは設定しないこともできる） |
| created_at | 登録日時 |

年齢は参考情報とし、対話難易度を自動的に決定する唯一の要素にはしない。
年齢は birthday から対話時に計算して導出し、年齢そのものは保存しない（経年による陳腐化を防ぐため）。

## 3-3. 登録時の生年月日入力

新規ユーザー（子ども・大人を問わず）を登録するとき、生年月日の入力を必須とする。

- 登録フォームでは年・月・日を分離して入力し、実在する日付であることを検証する。
- 過去の日付のみを許容し、未来の日付はエラーとする。
- 生年月日は家庭内環境のみへ保存し、外部サービスへ送信しない。
- 登録後に生年月日が未登録の利用者（本要件以前の登録者）がいた場合は、保護者画面で入力を促す。
- 生年月日の閲覧・修正・削除は保護者画面からのみ行う。

算出した年齢は会話レベルの参考材料として対話エンジンへ渡す。
使い方については 4-4 を参照のこと。

## 3-4. ユーザーの切り替え

- アプリ起動時にユーザー（子ども・大人）を選択する。
- 誤操作によるアカウント混在を防ぐため、利用中のユーザーを明示する。
- 保護者設定へのアクセスにはPIN等の保護を設ける。

# 4. F02：音声対話システム

このアプリの中核機能である。

## 4-1. 基本的な対話フロー

```text
       子どもが話す
             │
             ▼
       マイク入力
             │
             ▼
       音声認識 STT
             │
             ▼
       対話コンテキスト構築
             │
             ▼
       ローカルLLM
             │
       ┌─────┴─────┐
       │           │
    発話内容     思考評価
       │           │
       ▼           ▼
    音声合成    対話記録
       │           │
       ▼           ▼
    スピーカー   報酬判定
```

実際には、発話内容と評価情報を別々に生成することを推奨する。

## 4-2. 対話の基本ルール

LLMには以下のルールを与える。

1. 一度に質問するのは原則1つ。
2. 子どもの発話を尊重する。
3. 間違いを否定しない。
4. 正解よりも考え方を評価する。
5. すぐに答えを教えない。
6. 必要に応じてヒントを段階的に提示する。
7. 子どもが疲れている場合は無理に続けない。
8. 適切なタイミングで正しい知識を教える。
9. 会話を長引かせるためだけの質問をしない。
10. 最後に子どもの考えや発見を簡潔に振り返る。

## 4-3. 対話状態管理

対話は以下の状態で管理する。

| 状態 | 内容 |
|---|---|
| INTRO | ミッション開始 |
| QUESTION | 質問提示 |
| THINKING | 子どもの回答待ち |
| HINT | ヒント提示 |
| EXPLORATION | 思考の深掘り |
| EXPLANATION | 知識の補足 |
| REVIEW | 振り返り |
| COMPLETE | ミッション終了 |

重要なのは、LLMに状態遷移を自由に決定させないことである。

LLMは回答や評価材料を生成し、アプリ側の対話制御エンジンが状態遷移を管理する。
これにより、対話の長期化や不適切な進行を抑制できる。

## 4-4. 会話レベルの参考材料としての年齢

ユーザー登録時に収集した生年月日から年齢を計算し、対話コンテキスト構築時に会話レベルの参考材料として渡す。

- プロンプトには「対象：小学生」「対象：大人」のような参考指示として含め、語彙・説明の具体度・例え話の選び方を調整する。
- 年齢のみでミッションや難易度を自動的に切り替えない（01-overview.md 設計原則4）。個人別の調整は Memory による。
- 生年月日が未登録の利用者には、中性の会話レベル（一般的な大人向け）で対話し、保護者に入力を促す。
- ユーザーや保護者が物言い・説明レベルの調整を要求した場合、年齢の参考指示よりその要求を優先する。

# 5. F03：キャラクターシステム

## 5-1. 初期キャラクター

MVPでは3種類に絞る。

| キャラクター | 役割 | 対話スタイル |
|---|---|---|
| はかせ | 知識・科学 | 好奇心を刺激する質問 |
| たんてい | 推理・論理 | 観察・仮説・検証 |
| アーティスト | 創造・想像 | 自由な発想を促す |

それぞれ独立したシステムプロンプトを持たせる。

## 5-2. キャラクター定義

```json
{
  "character_id": "detective",
  "name": "たんてい",
  "description": "推理が大好きな探偵",
  "personality": [
    "観察力が鋭い",
    "好奇心旺盛",
    "少し慎重"
  ],
  "thinking_style": [
    "原因と結果を考える",
    "複数の可能性を比較する"
  ],
  "voice": {
    "engine": "voicevox",
    "speaker_id": 0,
    "speed_scale": 1.0,
    "pitch_scale": 0.0
  }
}
```

VOICEVOXの話者IDは設定ファイルで管理し、特定の話者に依存しない設計とする。
音声ライブラリの利用規約・各話者の利用条件も確認する。

# 6. F04：ミッションシステム

## 6-1. ミッション分類

MVPでは以下の3種類を実装する。

| ミッション | 育成対象 | 内容 |
|---|---|---|
| なぜなぜ探検 | 好奇心・論理 | 身近な疑問を考える |
| なぞとき探偵 | 推理・仮説 | 状況から答えを推測する |
| もしもワールド | 想像力・創造力 | 仮定の世界を考える |

大人ユーザー向けの拡張カテゴリとして、スキル習得ミッション（Python学習など）を追加する。
詳細は 6-5 を参照のこと。

## 6-2. ミッションの構成

```json
{
  "mission_id": "why_001",
  "category": "curiosity",
  "title": "空はどうして青い？",
  "difficulty": 1,
  "target_skills": [
    "hypothesis",
    "reasoning"
  ],
  "character_id": "professor",
  "estimated_minutes": 3,
  "initial_question": "空はどうして青いと思う？",
  "completion_conditions": [
    "child_has_shared_an_idea"
  ]
}
```

## 6-3. ミッション生成方針

以下のハイブリッド方式を採用する。

- 定番問題：事前定義された問題データベース
- 日替わり問題：LLMによる生成
- 個人最適化：子どもの興味・過去の会話から生成

MVPでは定番問題とLLMによる追加生成を組み合わせる。
最初から完全自動生成に依存すると、問題品質や難易度にばらつきが出るためである。

## 6-4. ミッション終了条件

以下のいずれかで終了する。

- 子どもが考えを説明した
- 必要なヒントを提示した
- 子どもが終了を希望した
- 保護者設定の利用時間に達した
- 一定時間応答がない

正解しなくてもミッションはクリア可能とする。

## 6-5. スキル習得ミッション（Python学習）

対象拡大の一環として、大人ユーザーが実務スキルを学べるミッションカテゴリを用意する。
最初のユースケースは Python とそのライブラリ活用である。

| ミッション | 育成対象 | 内容 |
|---|---|---|
| Python探求 | 実践的技能・論理 | 構文・標準ライブラリを対話で確かめながら学ぶ |
| ライブラリ活用 | 実践的技能 | requests・pandas等の選定理由と使い方を考える |
| コードレビューごっこ | 批判的思考 | 提示されたコードの問題点と改善案を説明する |

運用方針：

- 教育方針は既存ミッションと同じく「答えを急がない」を徹底する。
  写経のように正解コードを提示するのではなく、期待する挙動の予想、エラーメッセージの読み方、
  ライブラリを選ぶ判断基準を言語化させる。
- 対話は音声を中心にしつつ、コード片段は画面表示と読み上げの両方で提示する。
- 会話レベルの参考材料として年齢を使う（4-4）。大人向けには仕事の実例や実用ライブラリを例に選ぶ。
- Memory に「すでに学んだ構文・ライブラリ・ハマったエラー」を記録し、次回のミッション生成と
  復習の出題に活かす（F06）。
- 実行環境の構築・コード実行は本アプリの範囲外とし、対話による理解と思考の促進に限定する。

# 7. F05：ゲーミフィケーション

## 7-1. スタンプ

MVPでは6種類程度を用意する。

| スタンプ | 獲得条件 |
|---|---|
| はじめの一歩 | 初めて自分の考えを話した |
| なぜなぜ博士 | 理由を説明した |
| ひらめき名人 | 独創的なアイデアを出した |
| 名探偵 | 複数の可能性を考えた |
| チャレンジャー | ヒントを使って再挑戦した |
| おはなし名人 | 自分の物語を作った |

獲得判定にはLLMの評価結果を利用するが、最終的な付与条件はアプリケーション側で検証する。
スタンプ獲得は同一条件で何度も繰り返せないようにする。

## 7-2. 今日の冒険

1日の基本的な利用体験を次のようにする。

```text
       今日の冒険
            │
       キャラクター選択
            │
       ミッション開始
            │
       音声で対話
            │
       ミッションクリア
            │
       スタンプ獲得
            │
       今日の発見を記録
            │
       今日の冒険終了
```

1日1〜3ミッション、1ミッション3〜5分を目安とする。
利用時間を増やすことを目的とした連続ミッションやログインボーナスは採用しない。

## 7-3. 図鑑

MVPではスタンプ一覧を中心とし、図鑑は簡易版とする。
将来的には、子ども自身の発言・発見・創作物を記録するコレクションへ発展させる。

# 8. F06：Memory・思考記録

長期的なアプリの価値を左右する機能である。
単なる会話履歴ではなく、子どもごとの情報を構造化して保存する。

## 8-1. Memoryの分類

| 種類 | 保存内容 |
|---|---|
| Interest | 好きなテーマ |
| Knowledge | 対話で扱った知識 |
| Discovery | 子ども自身が発見したこと |
| Thinking | 思考の特徴・傾向 |
| Preference | 好きなキャラクター・対話形式 |
| Open Question | まだ解決していない疑問 |

## 8-2. 記録例

```json
{
  "child_id": "child_001",
  "type": "discovery",
  "topic": "宇宙",
  "content": "月は自分で光っているのではなく、太陽の光を反射していると理解した",
  "source": "mission_20261120_001",
  "created_at": "2026-11-20"
}
```

## 8-3. Memoryの利用

次回のミッション生成時に利用する。

例：

> 「前に月について話したよね。今日は月の形が毎日変わる理由を考えてみよう！」

こうして、過去の対話と新しい疑問を結びつける。

なお、LLMが推測した理解度を確定した知識として保存しないことが重要である。
「理解した」「知っている」といった情報は、子どもの発言など根拠を伴う形で記録する。

# 9. F07：保護者向け管理機能

MVPで実装するのは次の機能である。

| 機能 | 内容 |
|---|---|
| ユーザー管理 | 子ども・大人の登録（生年月日必須）・編集 |
| 利用時間 | 1日あたりの利用上限 |
| 会話履歴 | 対話内容の確認 |
| 利用状況 | 利用時間・ミッション数 |
| 成長記録 | 今日の発見・思考記録 |
| 設定 | キャラクター・音声設定 |

特に、保護者向け画面では「今日の発見」を優先的に表示する。

子どもの思考を点数化したり、兄弟間でランキングを作ったりする機能は設けない。
